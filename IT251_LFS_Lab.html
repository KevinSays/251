Start here

What this project is

Every distro you've used (Ubuntu, Fedora, Debian) was built by someone running thousands of compile commands. LFS has you run them yourself, in order, with an explanation for each one.

  • Build a cross-toolchain (compiler, linker, C library) that can't accidentally pick up your host system's files
  • Use it to build temporary tools, then step inside your new system with chroot
  • Compile the real system: about 80 packages, from glibc and GCC to systemd and bash
  • Configure it, compile a kernel, install a bootloader, and boot it
Analogy

Building a kitchen with borrowed tools

Your Debian VM is a borrowed kitchen. First you use its tools to forge your own knives (the cross-toolchain, Chapters 5–6). Then you move into an empty room and use only your knives to build the rest (chroot, Chapters 7–8). The careful separation keeps anything from the borrowed kitchen from leaking into yours. That's why the book is so strict about which user you are and which directory you're in.

How it fits Linux+

The lectures (9.1, 10.1, …) stay on Ascend Modules 5–7. The build reuses everything from Modules 1–4, from the inside: partitions and filesystems, mounts, users and groups, permissions, environment variables, the FHS (you'll create it by hand), the boot process, kernel modules, systemd. It also gives you concrete examples of security (least privilege, password hashing, chroot) and automation (every package is a shell script).

Be honest with your calendar. Six lab sessions are for learning, checkpoints, and getting unstuck. Most of the compiling happens between classes, often overnight. On 9.2 you'll measure your own laptop's speed and calculate how many hours your build will take. Plan around that number.

The book

Work from the official book, LFS 13.1-systemd: linuxfromscratch.org/lfs/view/13.1-systemd. This page doesn't replace it. It tells you which sections to do each week, adds class-specific warnings, and explains why things matter. When this page and the book seem to disagree, check this page's warnings first (they exist because our VM setup differs from the book's examples), then ask.

Make sure it says "systemd". The LFS site also has a "System V" edition. Make sure the book header says Version 13.1-systemd, and use the wget-list-systemd file, not plain wget-list.

Everyone builds on the same prepared Debian 13 VM, so we all start from the same, tested setup. Do all of this before the first lab day.

What the class VM is

The class VM (IT251-LFS-host-deb13-lfs13.1.ova) is a minimal, console-only Debian 13 "trixie" system that your instructor prepared as the host you build LFS from. LFS needs a host Linux with specific build tools at specific versions. This VM already passes the book's host check (§2.2), so nobody loses the first lab day fixing their distro. It is not LFS itself: you build LFS on a second, blank disk that you add in step 3.

Every session · keep long builds alive

Work inside tmux

A build runs inside your SSH window. If that window closes, your Wi-Fi drops, or you close your laptop's terminal, the build is killed halfway. tmux fixes this: it keeps your session running inside the VM, and you can reconnect to it later. Start it first every time you sit down to build, as student, before sudo -i:

tmux new -s lfs          # first time: start a session named "lfs"
tmux attach -d -t lfs    # every time after: reconnect to it (also after an SSH drop)
  • To leave a build running and close the window, press Ctrl+b, let go, then press d ("detach"). The build keeps going.
  • A green bar at the bottom of the window means you're inside tmux.
  • If tmux attach says no sessions, the VM was rebooted (that ends tmux too). Start a new one, run your resume card, and redo the package you were on.
  • Why the -d? It kicks off any old connection that's still hanging on to your session. That happens most after you save the VM's state in VirtualBox ("Save the machine state" when you close it) in the middle of a build. Saving the state is safe: the build is frozen and picks up right where it stopped when you start the VM again. But your old SSH window died while the VM was frozen, and tmux may still think it's there. If you reconnect with a plain tmux attach, part of your screen fills with rows of dots (·····), because tmux is sizing everything to the old, dead window. Nothing is broken. Press Ctrl+b, let go, press d, then run tmux attach -d -t lfs.
  • tmux can't help if your laptop goes to sleep, because the whole VM pauses. See Keep your laptop awake.

From your second session on · keep these open

Resume cards: coming back after a break

The book is "designed to be built in one session." You will shut your laptop many times, so every time you come back, a few things must be set up again (§2.3). Use the card for the chapter you're in. Skipping this is the #1 way people break their builds.

First lab day? You don't need these yet. Lab 9.2 creates the LFS disk, the lfs user and its environment, which are exactly what these cards check. Run through them only after you've finished 9.2. From then on, every time you sit down: start tmux, then the card for the chapter you're in.
You're working on…Use
Chapters 2–4 (finishing 9.2)Card 1
Chapters 5–6 (9.2 homework, 10.2)Card 1, then Card 2
Chapter 7 onward (11.2 and later)Card 1, then Card 3
Card 1 · Chapters 2–4 · root on the host 
sudo -i                  # root; the class VM already sets LFS and umask for root
echo $LFS                # must print /mnt/lfs
findmnt $LFS             # must show /dev/sdb1   (STOP if either line is empty)

After 9.2 your LFS partition mounts automatically at boot (we add it to Debian's /etc/fstab). If findmnt shows nothing, run mount -v -t ext4 /dev/sdb1 $LFS.

Card 2 · Chapters 5–6 · user lfs, never root 
sudo -i                  # Card 1 checks first, then:
su - lfs                 # the "-" matters: it loads the clean build environment
echo $LFS $LFS_TGT       # /mnt/lfs x86_64-lfs-linux-gnu
echo $PATH               # must START with /mnt/lfs/tools/bin

In the book's words, building these chapters as anyone else risks "installing packages to the host, and potentially rendering it unusable." Your prompt should look like lfs:~$.

Card 3 · Chapters 7–10 · root on the host, then chroot 
sudo -i                  # Card 1 checks first, then mount the virtual filesystems (§7.3):
mount -v --bind /dev $LFS/dev
mount -vt devpts devpts -o gid=5,mode=0620 $LFS/dev/pts
mount -vt proc proc $LFS/proc
mount -vt sysfs sysfs $LFS/sys
mount -vt tmpfs tmpfs $LFS/run
# + the /dev/shm lines at the end of §7.3.2
findmnt -R $LFS          # should list dev, dev/pts, proc, sys, run under /mnt/lfs

Then enter with the full chroot command from §7.4. Your prompt becomes (lfs chroot) root:/#. Only mount these once per boot; mounting them twice causes confusing errors.

Linux+ bonus: these cards are exam material in disguise: bind mounts, virtual filesystems (/proc, /sys, devpts, tmpfs), environment variables, and su - vs. su. Be ready to explain each line.

Protect your hours

Snapshots & backups

A failed build late in Chapter 8 shouldn't cost you three weeks. Take these VirtualBox snapshots with the VM shut down:

SnapshotWhenProtects
readyAfter Get ReadyClean import + sources
ch4-readyEnd of Ch. 4Partition, lfs user, environment
ch6-temptoolsEnd of Ch. 6The whole cross-toolchain
ch7-backupEnd of Ch. 7 (+ the §7.15 tarball)A working chroot system
pre-gccBefore §8.32An interrupted GCC build
pre-bootBefore Ch. 10 GRUBYour host's bootloader

How to take a snapshot

  1. Get out of the chroot if you're in it: type exit until the prompt no longer says (lfs chroot).
  2. Shut the VM down from its terminal: sudo poweroff. Wait until VirtualBox shows the VM as Powered Off.
  3. In the VirtualBox Manager window, click your VM, then open its Snapshots view. (Depending on your VirtualBox version, that's the list/menu button next to the VM's name, or Machine → Tools → Snapshots.)
  4. Click Take, type the name from the table above (e.g. ch6-temptools), and click OK.
  5. Start the VM again and run your resume card.

To go back to a snapshot: power the VM off, open the same Snapshots view, click the snapshot, and choose Restore. Everything after that snapshot is lost, so note in your journal where you're starting again.

Keep your laptop awake during long builds

When your laptop sleeps, the VM freezes, and a build that's interrupted that way often has to be redone. Before any long build, plug in and turn off automatic sleep:

LaptopHow
Windows 11Settings → System → Power & battery → Screen and sleep (newer versions: Screen, sleep & hibernate timeouts): set the plugged in sleep option to Never. Closing the lid can still sleep it, so leave it open.
macOSOpen Terminal and run caffeinate -i. Your Mac stays awake until you press Ctrl+C or close that window. Leave the lid open.
LinuxIn your desktop's Settings → Power, turn off Automatic suspend while plugged in.

The screen turning off by itself is fine. Only sleep stops the VM.

Snapshot vs. backup, again. A VirtualBox snapshot saves the whole VM, on your laptop's disk. The §7.15 tarball saves just the LFS filesystem, as a file. If your laptop's drive dies, both are gone. That's why real backups live on a different device. Snapshots also use disk space, so delete old ones once you're safely past them.

Fell behind?

The catch-up snapshot

If you aren't inside the chroot by 12.2, or your build is damaged beyond repair, your instructor can give you a finished end-of-Chapter-7 system. You start Chapter 8 from there and still build, configure, and boot your own system.

The rules

  • Ask first. Your instructor tells you when to use it: at the 12.2 checkpoint, or later if your build can't be recovered. The file (lfs-temp-tools-13.1-systemd.tar.xz, 1.2 GB, plus a .sha256) is on the class GitHub Release. It's public, but using it without your instructor's OK still counts as using it.
  • Once per student. After that, use your own snapshots.
  • Grading: you keep full credit for milestones you already earned. Milestones the snapshot skips (M2 and/or M3) earn half credit. Your journal must explain what went wrong, and still answer the "why" questions from Chapters 5–7: why the toolchain is built twice, what env -i protects against, and why chroot isn't a security boundary.
  • It contains a marker file, /etc/it251-catchup. That's expected; you'll show it at your boot demo.

How to use it

You need the 9.2 disk setup done (your /dev/sdb1 and its fstab line). First, as student (your normal login, not root), download both files straight into the VM. It's 1.2 GB, so give it a few minutes:

cd ~
wget https://github.com/KevinSays/251/releases/download/lfs-catchup-13.1/lfs-temp-tools-13.1-systemd.tar.xz
wget https://github.com/KevinSays/251/releases/download/lfs-catchup-13.1/lfs-temp-tools-13.1-systemd.tar.xz.sha256

(If your instructor hands it out on a USB stick instead, copy it in with scp -P 2222 lfs-temp-tools-13.1-systemd.tar.xz* student@127.0.0.1: from your laptop.) Then as root on the Debian host, not in chroot:

sudo -i
cd ~student && sha256sum -c lfs-temp-tools-13.1-systemd.tar.xz.sha256
U=$(blkid -s UUID -o value /dev/sdb1)     # remember the partition's UUID
umount -R /mnt/lfs                        # unmount it (and any virtual filesystems)
findmnt -R /mnt/lfs                       # must print nothing
mkfs -v -t ext4 -U "$U" /dev/sdb1         # wipe ONLY sdb1, keeping the same UUID
mount /mnt/lfs                            # uses your fstab line from 9.2
cd /mnt/lfs && tar -xpf ~student/lfs-temp-tools-13.1-systemd.tar.xz
cat /mnt/lfs/etc/it251-catchup            # confirms the restore

Two things that look like problems but aren't:

  • The mkfs line stops and asks /dev/sdb1 contains a ext4 file system … Proceed anyway? (y,N). It's warning you that your old build is on that partition, and wiping it is the point. Check that it says /dev/sdb1, then type y and press Enter. (If it names any other device, press Enter to cancel and ask your instructor.)
  • The tar line prints nothing for a few minutes while it unpacks. Wait for the prompt to come back.

Then run Card 3, enter the chroot, and start Chapter 8. Take snapshot ch7-backup first.

Why not the book's restore? §7.15's restore deletes everything with rm -rf ./* as root. If it runs in the wrong directory, it wipes your Debian host. Reformatting just /dev/sdb1 can only ever touch the LFS disk. Double-check the device name: it's sdb1, never sda.

When it breaks

Common snags

Before asking for help, collect three things: the book section, the exact command you ran, and the last ~30 lines of output. That's how to ask in class, on the course discussion board, or on the LFS support channels.

SymptomLikely cause → fix
$LFS is emptyYou're in a new shell. Run the resume card. Never run root commands from the book with an empty $LFS.
Ch. 5–6 "Permission denied"Usually a sign you're doing it right, as lfs, but a step was skipped: check the §4.3 chown commands ran. If you got around it by using root, stop and ask.
Wrong compiler / "not found"Not in the clean environment. Card 2: su - lfs (with the dash); echo $PATH must start with /mnt/lfs/tools/bin.
Build fails halfwayDelete the package directory, re-extract, start the package over. Compare each command with the book character by character. To read the error clearly, rerun with make -j1.
Laptop slept / rebooted mid-buildRun your resume card, then redo that package from a fresh extract. Next time, turn off sleep first.
SSH window closed or Wi-Fi dropped during a buildIf you were inside tmux, SSH back in and run tmux attach -d -t lfs; the build kept going. If you weren't, the build was killed: run your resume card and redo that package from a fresh extract. Use tmux from now on.
Screen full of dots (·····) after reconnectingThat's tmux, not your build. It happens after you saved the VM's state, or your SSH window died, and you reconnected with a plain tmux attach: tmux is still sizing the screen to your old, dead window and fills the rest with dots. Press Ctrl+b, then d, and run tmux attach -d -t lfs (the -d kicks the old window off). Your build was never affected. See Work inside tmux.
VM or laptop shut off mid-chapter: did it finish?Don't redo anything yet. Run your resume card, then check two things: (1) ls -d $LFS/sources/*/ lists leftover package folders. "No such file or directory" means none are left; a folder that is listed is the package that was interrupted. (2) Check the last thing the chapter's last package makes, e.g. end of Ch. 6: ls -l $LFS/usr/bin/cc. If it's there and no folders are left, the chapter finished. Otherwise delete the leftover folder and redo just that package (and any after it) from a fresh extract.
"No space left on device"df -h /mnt/lfs. You probably forgot to delete extracted source directories in $LFS/sources. Old snapshots can also fill your laptop's disk.
Hundreds of test failures (Binutils/GCC)Usually no pseudo-terminals: devpts isn't mounted. Exit the chroot, check findmnt $LFS/dev/pts, redo Card 3. See §4.6.
"mount point does not exist" / weird chroot errorsVirtual filesystems not mounted, or mounted twice. Check findmnt -R $LFS.
My build is beyond repairFirst try your most recent VirtualBox snapshot. If that doesn't help, ask about the catch-up snapshot.
md5sum: FAILEDThe download was corrupted or cut off. Delete that file and run wget --input-file=wget-list-systemd --continue again.
Debian boots to emergency mode, or says "the root account is locked"The class VM has no root password, so you can't use the emergency prompt; that's expected. Power the VM off. In Settings → Storage, check that lfs.vdi is still attached on SATA port 1 and the OS disk on port 0, then boot again. Still stuck? Restore your latest snapshot and tell your instructor. (Usually caused by an /etc/fstab line without nofail, or a missing LFS disk.)
Can't SSH to port 2222VM not fully booted, or another VM is using port 2222. Use the VirtualBox console meanwhile.
