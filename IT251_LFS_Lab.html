Start here

What this project is

Every distro you've used (Ubuntu, Fedora, Debian) was built by someone running thousands of compile commands. LFS has you run them yourself, in order, with an explanation for each one.

  • Build a cross-toolchain (compiler, linker, C library) that can't accidentally pick up your host system's files
  • Use it to build temporary tools, then step inside your new system with chroot
  • Compile the real system: about 80 packages, from glibc and GCC to systemd and bash
  • Configure it, compile a kernel, install a bootloader, and boot it
Analogy

Building a kitchen with borrowed tools

Your Debian VM is a borrowed kitchen. First you use its tools to forge your own knives (the cross-toolchain, Chapters 5–6). Then you move into an empty room and use only your knives to build the rest (chroot, Chapters 7–8). The careful separation keeps anything from the borrowed kitchen from leaking into yours. That's why the book is so strict about which user you are and which directory you're in.

How it fits Linux+

The lectures (9.1, 10.1, …) stay on Ascend Modules 5–7. The build reuses everything from Modules 1–4, from the inside: partitions and filesystems, mounts, users and groups, permissions, environment variables, the FHS (you'll create it by hand), the boot process, kernel modules, systemd. It also gives you concrete examples of security (least privilege, password hashing, chroot) and automation (every package is a shell script).

Be honest with your calendar. Six lab sessions are for learning, checkpoints, and getting unstuck. Most of the compiling happens between classes, often overnight. On 9.2 you'll measure your own laptop's speed and calculate how many hours your build will take. Plan around that number.

The book

Work from the official book, LFS 13.1-systemd: linuxfromscratch.org/lfs/view/13.1-systemd. This page doesn't replace it. It tells you which sections to do each week, adds class-specific warnings, and explains why things matter. When this page and the book seem to disagree, check this page's warnings first (they exist because our VM setup differs from the book's examples), then ask.

Make sure it says "systemd". The LFS site also has a "System V" edition. Make sure the book header says Version 13.1-systemd, and use the wget-list-systemd file, not plain wget-list.

  4. First login: start the VM and log in as student / lfs-student. You'll be made to set your own password right away.
  5. Use SSH so you can copy and paste (strongly recommended). From your laptop's terminal (Windows Terminal, macOS Terminal, or Linux): 
    ssh -p 2222 student@127.0.0.1
    If you change your password over SSH, it disconnects you afterward, so just log in again. If SSH won't connect, check that no other VM (like your Proxmox lab) is running and using port 2222.
  6. Check the host (this is part of milestone M1):

    mkdir -p ~/lfs-sources && cd ~/lfs-sources
wget https://www.linuxfromscratch.org/lfs/view/13.1-systemd/wget-list-systemd

md5sum -c md5sums | grep -v ': OK$'      # no output = every file is good
    If a file says FAILED or is missing, run the wget --input-file line again. If a download site is down, use a mirror.
  8. Refresh apt once. The VM ships without package lists (to keep the file small), so sudo apt install fails until you run sudo apt update. Do that now, and while you're at it install the tools for configuring the kernel later (13.2):

Two disks, one rule. sda is the Debian system you're working from. sdb is the LFS system you're building. The book's examples say things like /dev/<xxx> or /dev/sda, but while you build, your LFS disk is /dev/sdb and its partition is /dev/sdb1. A command aimed at the wrong disk can wipe your host VM.

Keep these open

Resume cards: coming back after a break

The book is "designed to be built in one session." You will shut your laptop many times, so every time you come back, a few things must be set up again (§2.3). Use the card for the chapter you're in. Skipping this is the #1 way people break their builds.

Card 1 · Chapters 2–4 · root on the host 
sudo -i                  # root; the class VM already sets LFS and umask for root
echo $LFS                # must print /mnt/lfs
findmnt $LFS             # must show /dev/sdb1   (STOP if either line is empty)

After 9.2 your LFS partition mounts automatically at boot (we add it to Debian's /etc/fstab). If findmnt shows nothing, run mount -v -t ext4 /dev/sdb1 $LFS.

Card 2 · Chapters 5–6 · user lfs, never root 
sudo -i                  # Card 1 checks first, then:
su - lfs                 # the "-" matters: it loads the clean build environment
echo $LFS $LFS_TGT       # /mnt/lfs x86_64-lfs-linux-gnu
echo $PATH               # must START with /mnt/lfs/tools/bin

In the book's words, building these chapters as anyone else risks "installing packages to the host, and potentially rendering it unusable." Your prompt should look like lfs:~$.

Card 3 · Chapters 7–10 · root on the host, then chroot 
sudo -i                  # Card 1 checks first, then mount the virtual filesystems (§7.3):
mount -v --bind /dev $LFS/dev
mount -vt devpts devpts -o gid=5,mode=0620 $LFS/dev/pts
mount -vt proc proc $LFS/proc
mount -vt sysfs sysfs $LFS/sys
mount -vt tmpfs tmpfs $LFS/run
# + the /dev/shm lines at the end of §7.3.2
findmnt -R $LFS          # should list dev, dev/pts, proc, sys, run under /mnt/lfs

Then enter with the full chroot command from §7.4. Your prompt becomes (lfs chroot) root:/#. Only mount these once per boot; mounting them twice causes confusing errors.

Linux+ bonus: these cards are exam material in disguise: bind mounts, virtual filesystems (/proc, /sys, devpts, tmpfs), environment variables, and su - vs. su. Be ready to explain each line.

Lab 9.2 · Session 1

Prepare the disk, the user, and measure your SBU

Week of Oct 19 · Book: Chapters 2–4, then §5.2 · Milestone M1 · Homework: finish Chapter 5

Step 1 · Read first (Ch. 1–2)

Skim §2.2 Host System Requirements. Your version-check.sh already passed, because the class VM was built to meet them. Read §2.3 carefully; it's the reason for the resume cards.

Step 2 · Partition the LFS disk (§2.4)

Become root and prove you have the right disk before touching it:

sudo -i
lsblk /dev/sdb           # must say 30G and show NO partitions under it

If sdb isn't 30G and empty, stop and ask. Then create one partition on a classic MBR ("dos") partition table:

fdisk /dev/sdb
  o        # new empty DOS (MBR) partition table
  n        # new partition
  p        # primary
  1        # partition number 1
  Enter    # default first sector
  Enter    # default last sector (use the whole disk)
  w        # write and quit
lsblk /dev/sdb           # now shows sdb1
Why MBR and not GPT? Our VMs boot with legacy BIOS. With an MBR disk, GRUB needs nothing extra. A GPT disk on BIOS needs an extra tiny "BIOS boot" partition (the book explains it in Chapter 10). Same result, fewer moving parts. We skip swap: the host VM already has some.

Step 3 · Filesystem, $LFS, mount (§2.5–2.7)

mkfs -v -t ext4 /dev/sdb1
echo $LFS ; umask        # /mnt/lfs and 0022 (the class VM sets both for root)
mount -v -t ext4 /dev/sdb1 $LFS
findmnt $LFS

Now make it mount automatically every boot. The nofail option means that if the disk is ever missing, Debian still boots instead of dropping you into emergency mode:

echo "UUID=$(blkid -s UUID -o value /dev/sdb1)  /mnt/lfs  ext4  defaults,nofail  0 0" >> /etc/fstab
systemctl daemon-reload
umount $LFS && mount -a && findmnt $LFS     # proves the fstab line works

Step 4 · Sources (§3.1)

Create the sources directory exactly as §3.1 says (mkdir + chmod a+wt). Then, instead of downloading again, copy what you downloaded at home and re-check it in its new home:

cp -v ~student/lfs-sources/* $LFS/sources/
cd $LFS/sources && md5sum -c md5sums | grep -v ': OK$' ; cd
chown root:root $LFS/sources/*

Step 5 · Layout, the lfs user, the clean environment (Ch. 4)

Do §4.2, §4.3 and §4.4 exactly as written. Things people miss:

  • §4.4 moves /etc/bash.bashrc out of the way. Debian has this file, so do that step.
  • §4.4 ends by adding MAKEFLAGS=-j$(nproc) to the lfs user's .bashrc and running source ~/.bash_profile. Do both.
  • Check yourself with Card 2: prompt lfs:~$, and $PATH starts with /mnt/lfs/tools/bin.
Why it matters

Least privilege, for real

The book builds Chapters 5–6 as a throwaway, unprivileged lfs user with a scrubbed environment (env -i). If a command is mistyped, it fails with "Permission denied" instead of overwriting files in your host's /usr. That's the same idea as running a web server as www-data instead of root, which is Module 5 material.

Step 6 · Measure your SBU (§4.5 + §5.2)

Read §4.5 About SBUs and General Compilation Instructions. The SBU (Standard Build Unit) is how long Binutils pass 1 takes on one core on your machine. Every other build time in the book is a multiple of it.

  1. Plug in your laptop and set it to performance power mode. Don't let it sleep.
  2. As lfs, follow §5.2. Extract the tarball and cd in, then create and enter build.
  3. Wrap the configure/make/install in time { … } as the book's note shows. Use make -j1 for this one package, because the SBU is defined on a single core: 
    time { ../configure --prefix=$LFS/tools ...(rest exactly as in §5.2)... && make -j1 && make install; }
  4. Write down the real time. That's your SBU.
  5. Clean up: cd $LFS/sources && rm -rf binutils-2.47. From now on, keep the book's normal MAKEFLAGS (all cores).

The cross-toolchain and temporary tools

The habit that saves you: General Compilation Instructions

For every package (re-read the page if unsure):

cd $LFS/sources
tar -xf <package>.tar.xz        # (or .gz) extract
cd <package>                    # enter it
# ...the book's commands for this package...
cd $LFS/sources
rm -rf <package>                # ALWAYS delete the extracted directory when done

If a build fails halfway, don't fix it in place. Delete the directory, extract again, and redo the whole package.

What's actually happening

Concept

Why build the compiler twice?

Your Debian GCC makes programs that link against Debian's C library. Chapter 5 builds a cross-compiler with a different name (x86_64-lfs-linux-gnu-gcc, from $LFS_TGT) that only looks inside $LFS. Because its name is different, nothing can accidentally use the host's tools or libraries. Chapter 6 uses it to build temporary tools that are already inside your new system. The Toolchain Technical Notes explain this in depth. Read them; they're the heart of LFS.

Checkpoint

The Chapter 5 sanity check (§5.5)

After Glibc, the book has you compile an empty C program with the new toolchain and inspect it with readelf. The output must name the new dynamic linker, [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]. If it doesn't, stop: everything after this depends on it. Screenshot it for M2.

Lab 11.2 · Session 3

Into the chroot

Week of Nov 2 · Book: Chapter 7 → start Chapter 8 · Milestone M3 · From here on: root and Card 3, never lfs · Homework: through §8.5 Glibc

User switch! Chapter 7 onward is done as root, not lfs (§7.2). Type exit to leave the lfs shell, then confirm whoami = root and echo $LFS = /mnt/lfs. Running §7.2's chown with an empty $LFS would change ownership on your host's /usr.

Steps

  1. §7.2 Changing ownership, then §7.3 virtual kernel filesystems (these are the Card 3 mounts).
  2. §7.4 Enter the chroot. Screenshot the (lfs chroot) root:/# prompt for M3.
  3. §7.5 and §7.6: you're building the FHS (Week 1!) and /etc/passwd / /etc/group (Week 4!) by hand.
  4. §7.7–7.14: Gettext, Bison, Perl, Zlib, mpdecimal, Python, Texinfo, Util-linux. Same compile habit as before.
  5. §7.15 Cleanup and backup. The backup is optional in the book, but required for this class. Follow its steps exactly: exit the chroot, unmount the virtual filesystems, then create the tarball in root's home. The book warns that compressing takes "over 10 minutes." Afterward, shut down and take snapshot ch7-backup.
  6. Re-enter the chroot (Card 3) and start Chapter 8.
Read the restore warning twice. §7.15's restore runs rm -rf ./* as root. With the wrong directory or an empty $LFS, the book says it "will destroy your entire host system." In this class, restore by reverting your VirtualBox snapshot instead; use the tarball only if your instructor tells you to.
Concept

chroot: a changed root, not a cage

chroot makes a process see /mnt/lfs as /, so programs inside find your new libraries and tools. But it is not a security boundary: root inside a chroot can escape it, and it shares the host's kernel, processes, and network. Containers (namespaces + cgroups) and SELinux/AppArmor exist to provide the real isolation chroot lacks. That's a classic Module 6 exam distinction.

Protect your hours

Snapshots & backups

A failed build late in Chapter 8 shouldn't cost you three weeks. Take these VirtualBox snapshots with the VM shut down:

SnapshotWhenProtects

Snapshot vs. backup, again. A VirtualBox snapshot saves the whole VM, on your laptop's disk. The §7.15 tarball saves just the LFS filesystem, as a file. If your laptop's drive dies, both are gone. That's why real backups live on a different device. (You saw the same rule in the Proxmox lab.) Snapshots also use disk space, so delete old ones once you're safely past them.

Fell behind?

The catch-up snapshot

If you aren't inside the chroot by 12.2, or your build is damaged beyond repair, your instructor can give you a finished end-of-Chapter-7 system. You start Chapter 8 from there and still build, configure, and boot your own system.

The rules

  • Ask first. Your instructor gives you the file (lfs-temp-tools-13.1-systemd.tar.xz plus a .sha256). It's offered at the 12.2 checkpoint, or later if your build can't be recovered.
  • Once per student. After that, use your own snapshots.
  • Grading: you keep full credit for milestones you already earned. Milestones the snapshot skips (M2 and/or M3) earn half credit. Your journal must explain what went wrong, and still answer the "why" questions from Chapters 5–7: why the toolchain is built twice, what env -i protects against, and why chroot isn't a security boundary.
  • It contains a marker file, /etc/it251-catchup. That's expected; you'll show it at your boot demo.

How to use it

You need the 9.2 disk setup done (your /dev/sdb1 and its fstab line). Copy the file into the VM (e.g. scp -P 2222 lfs-temp-tools-13.1-systemd.tar.xz* student@127.0.0.1:), then as root on the Debian host, not in chroot:

sudo -i
cd ~student && sha256sum -c lfs-temp-tools-13.1-systemd.tar.xz.sha256
U=$(blkid -s UUID -o value /dev/sdb1)     # remember the partition's UUID
umount -R /mnt/lfs                        # unmount it (and any virtual filesystems)
findmnt -R /mnt/lfs                       # must print nothing
mkfs -v -t ext4 -U "$U" /dev/sdb1         # wipe ONLY sdb1, keeping the same UUID
mount /mnt/lfs                            # uses your fstab line from 9.2
cd /mnt/lfs && tar -xpf ~student/lfs-temp-tools-13.1-systemd.tar.xz
cat /mnt/lfs/etc/it251-catchup            # confirms the restore

Then run Card 3, enter the chroot, and start Chapter 8. Take snapshot ch7-backup first.

Why not the book's restore? §7.15's restore deletes everything with rm -rf ./* as root. If it runs in the wrong directory, it wipes your Debian host. Reformatting just /dev/sdb1 can only ever touch the LFS disk. Double-check the device name: it's sdb1, never sda.

When it breaks

Common snags

Before asking for help, collect three things: the book section, the exact command you ran, and the last ~30 lines of output. That's how to ask in class, on the course discussion board, or on the LFS support channels.

SymptomLikely cause → fix
$LFS is emptyYou're in a new shell. Run the resume card. Never run root commands from the book with an empty $LFS.
Ch. 5–6 "Permission denied"Usually a sign you're doing it right, as lfs, but a step was skipped: check the §4.3 chown commands ran. If you got around it by using root, stop and ask.
Wrong compiler / "not found"Not in the clean environment. Card 2: su - lfs (with the dash); echo $PATH must start with /mnt/lfs/tools/bin.
Build fails halfwayDelete the package directory, re-extract, start the package over. Compare each command with the book character by character. To read the error clearly, rerun with make -j1.
Laptop slept / rebooted mid-buildRun your resume card, then redo that package from a fresh extract.
"No space left on device"df -h /mnt/lfs. You probably forgot to delete extracted source directories in $LFS/sources. Old snapshots can also fill your laptop's disk.
Hundreds of test failures (Binutils/GCC)Usually no pseudo-terminals: devpts isn't mounted. Exit the chroot, check findmnt $LFS/dev/pts, redo Card 3. See §4.6.
"mount point does not exist" / weird chroot errorsVirtual filesystems not mounted, or mounted twice. Check findmnt -R $LFS.
My build is beyond repairFirst try your most recent VirtualBox snapshot. If that doesn't help, ask about the catch-up snapshot.
md5sum: FAILEDThe download was corrupted or cut off. Delete that file and run wget --input-file=wget-list-systemd --continue again.
Debian boots to emergency modeThe LFS disk is missing or moved and its fstab line lacks nofail. Log in as root at the emergency prompt and fix /etc/fstab.
Can't SSH to port 2222VM not fully booted, or another VM is using port 2222. Use the VirtualBox console meanwhile.
