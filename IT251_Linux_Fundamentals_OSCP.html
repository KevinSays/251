Framing

Why the same material reads differently

Everything below is Linux+ material you've already touched this term. A sysadmin cares about it because it's their job to keep the box running. A pentester cares about the exact same facts because after an exploit lands, the very first thing you have is usually a bare, ugly shell on someone else's machine — no menus, no GUI, and no idea yet what you're standing on. Every fact in this page doubles as an answer to the question a pentester is actually asking in that moment: what is this box, what can I see, and what can I touch?

Foundations

The kernel, user space, and why that split matters to you

"Linux" technically names only the kernel — the program that talks to hardware, schedules processes, and enforces permissions. Everything you actually type is user space: GNU utilities, the shell, whatever service got you a foothold. Week 1 covered this split as part of the boot sequence (firmware → bootloader → kernel → systemd). The pentest reason to care: the kernel version is a dated, fingerprint-able fact about a box, and an old kernel is a map of every local privilege-escalation exploit that shipped for it.

First move

Fingerprint the box before you do anything else

$ uname -a
Linux target 5.4.0-100-generic #113-Ubuntu SMP ... x86_64 GNU/Linux
$ cat /etc/os-release

That single line tells you the kernel release and architecture — enough to go check searchsploit or a CVE database for a matching local-root exploit before you spend an hour hunting for one by hand. It's the same command Week 1 introduced for basic system enumeration; here it's the opening move of an engagement instead of a troubleshooting step.

Device files

/dev, /proc, and /sys aren't just plumbing

/proc/ is a live, readable window into every running process — command lines, open files, environment variables, memory maps — all exposed as plain text files, no special tooling required. cat /proc/<pid>/cmdline can hand you a password that got passed as a command-line argument instead of piped in safely. That's not a bug in the kernel; it's the kernel doing exactly what it's supposed to do (expose process state to user space) in a way that happens to leak secrets when an application is careless.

Access

The command line is the whole interface, not a shortcut to one

Week 2 covered shell config load order and environment variables as things you configure on your own machine. On someone else's box, post-exploit, that same shell knowledge answers a much blunter question: is this shell actually usable, and can I trust anything it tells me?

Reality check

A reverse shell is not a terminal

A raw reverse or bind shell from a web exploit is missing almost everything a normal terminal gives you for free: no job control, no tab completion, no arrow-key history, and it dies the instant a network hiccup drops the TCP connection. Upgrading it to a real TTY is routine, current OSCP practice — not a party trick:

$ python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl-Z to background it, then on your attacking box:
$ stty raw -echo; fg
# back in the shell:
$ export TERM=xterm-256color
$ stty rows <n> columns <n>

Notice this only works because pty is a Python standard-library module wrapping a kernel feature (pseudo-terminals) — the same "everything is a file" device-file model /dev/ exposes. Fundamentals, not magic.

PATH abuse

$PATH is a search order, and search orders can be gamed

Week 2 explained $PATH as "which directory the shell checks, in order, to resolve a bare command name." From an offensive angle: if a privileged script or SUID binary calls another program by name (not full path) and a directory earlier in your $PATH is writable, you can drop a malicious file with that name and get it executed with elevated rights instead. This is a real GTFOBins-style technique, not a hypothetical — and it only makes sense once you already understand PATH resolution as a mechanism, which you do.

Terrain

The FHS is a map — and pentesters read maps for loot, not tidiness

Lab 3's scavenger hunt already had you locate files across the Filesystem Hierarchy Standard. The directories don't change meaning on an engagement; what changes is what you're looking for in each one.

DirectorySysadmin reads it asPentester reads it as
/etc/Configuration filesApplication configs that often embed plaintext credentials, plus /etc/passwd and /etc/shadow for account and hash enumeration
/home/, /root/Personal filesSSH keys in ~/.ssh/, shell history files, saved credentials in dotfiles
/var/Logs, spools, cachesWeb server logs and webroots (/var/www/) — often where your initial foothold's source code lives
/tmp/Scratch space, cleared at bootWorld-writable by default — a natural place to stage a payload or exploit binary you upload
/opt/Third-party applicationsOften the least-patched software on the box, since it bypasses the distro's own package manager
/dev/, /proc/, /sys/Kernel-exported device and process dataFree, tool-free enumeration — readable without installing anything on the target

Still one hierarchy

None of this changes the FHS itself — it's the same single rooted tree Week 1 covered, and the same directories mean the same things on every distro that follows the standard. What changes is the question you're asking as you walk it.

Toolbox

Useful commands, sorted by what a foothold shell needs first

The source material this page is organized against groups commands by category: text/search, processes, permissions, system info, hardware. That's still the right grouping — here's the same categories with the pentest "why."

Text & search

grep, find — hunting instead of filtering

Lab 4 used grep and find against known data to practice pattern matching. Point the exact same commands at an unfamiliar filesystem and they become a search for anything interesting a previous admin left behind:

$ grep -ri "password" /etc /var/www 2>/dev/null
$ find / -perm -4000 -type f 2>/dev/null

That second command lists every SUID binary on the box — programs that run with their owner's permissions rather than the caller's. Cross-reference an unfamiliar result against GTFOBins; if it's listed there, GTFOBins hands you the exact command to leverage it into a root shell. This is current, standard practice, not a dated trick.

Processes

ps aux — who else is on this box, doing what

Week 4 covered process states and job control for managing your own work. On a foothold box, ps aux answers a different question: what's running as root that you could interact with, and is there a cron job (Lab 4 territory again) quietly running a script as root on a schedule that you can tamper with before it fires?

Permissions

rwx, setuid, and setgid — the same bits, an offensive reading

Week 3/4 covered chmod/chown and the setuid/setgid/sticky bits as an access-control system to configure correctly. From the other side of that system: a setuid-root binary is a standing offer — if you can make it do something its author didn't intend, you inherit root's permissions for as long as it runs. That's precisely why find / -perm -4000 above is one of the first commands run on almost every Linux privilege-escalation path. Same octal math (chmod 4755), opposite intent.

System info

id, whoami, hostname — know your own footing first

Before enumerating the box, enumerate yourself. id shows your UID, GID, and every group you belong to — a user in the docker or lxd group, for instance, usually has an easy path to root even without a single exploit, because those groups grant control over containers that can mount the host filesystem. This is the same command Week 1 used for basic account checks; on a foothold shell it's the very first thing you run, before anything else.

Hardware

lspci, lsusb — lower priority, still occasionally the answer

Hardware enumeration matters far less against a remote server than it does on a physical machine or lab VM you have console access to, but it hasn't gone away: it's how you notice you're inside a VM in the first place (a hint about isolation and what else might be reachable), and it's still how Week 1's device-file material (block vs. character devices) gets confirmed on a system you didn't build yourself.
