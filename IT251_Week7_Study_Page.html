Overview

What Week 7 covers

Everything up to now has been "here's how a piece works." This week flips the question to "it's broken — where do you look first?" Troubleshooting is 22% of the XK0-006 exam, second only to System Management, and it's tested as scenario-based questions, not recall — which means the actual skill here is knowing which tool answers which kind of question, fast, under a "something's wrong" prompt instead of a "how do I" prompt.

  • Read boot and service logs with journalctl, including scoping to a unit or a specific boot
  • Read kernel/hardware messages with dmesg
  • Use ss to check connection state, not just what's listening
  • Capture and read basic packet traffic with tcpdump
  • Trace a network path with traceroute/tracepath
  • Read CPU/memory/I/O load with top, vmstat, iostat, and free
Why this week, not a whole new module: a lot of this is remedial to material you already have — journalctl showed up briefly in Week 5, ss in Week 2, /var/log in Week 1. This session collects those threads, fills in the pieces that were missing (dmesg, tcpdump, traceroute, structured performance reading), and reframes all of it around "diagnose," which is how the exam actually asks about it. As always, this page is a conceptual supplement — your hands-on reps for these tools happen in ExtremeLabs, and Ascend has the full-depth reading if a topic here needs more than survey-level.

Applied

Worked examples

Think it through before you expand the answer.

Boot logs

It crashed before you could read the screen

A box rebooted unexpectedly overnight. By the time you're logged back in, the on-screen boot messages are long gone. How do you see what happened during that boot specifically, not the current one?

Show answer 
journalctl -b -1

-b scopes to one boot; -1 means "the boot before this one" (-2 the one before that, and so on — systemd numbers boots for exactly this reason). Add -p err to cut the noise down to errors and worse while you're hunting for what actually failed.

Hardware

A USB drive isn't showing up

You plug in a USB drive. Nothing appears in lsblk. Where do you look to see whether the kernel even noticed the device was plugged in?

Show answer 
dmesg -T | tail -30

dmesg reads the kernel ring buffer — the low-level hardware/driver messages that show up the instant a device is detected (or fails to be), before anything at the filesystem or systemd level gets involved. -T converts the raw kernel timestamps to human-readable ones. If there's nothing about the device here at all, the problem is likely the cable/port/hardware, not Linux.

Connection state

Not "connection refused" — just hanging

A client trying to reach a service on this box doesn't get refused — the connection just hangs and eventually times out. ss -tuln confirms the service is listening. What's the next thing to check locally before blaming the network?

Show answer 
ss -tanp

Dropping -l (listening-only) and adding -a (all sockets) and -p (owning process) shows every connection's actual state — SYN-SENT, ESTABLISHED, and so on. A pile of connections stuck in SYN-RECV points at a firewall silently dropping the handshake rather than rejecting it outright — "refused" and "silently dropped" look identical to the user but mean different fixes.

Network path

Reaches some sites, not others

From this box, ping 1.1.1.1 works, but a specific internal server times out. Both are pingable IPs, so where does the packet actually stop?

Show answer 
traceroute 10.20.30.40

traceroute shows the hop-by-hop path and where replies stop coming back — the last hop that answered is the last point you know traffic actually reached. That turns "the network is broken" into "hop 4, which is this specific router/firewall, is where it dies," which is a ticket someone can actually act on.

Packet capture

Is it even arriving?

ss shows a service listening, traceroute shows a clean path, but a client still can't connect. What's the last-resort tool, and what does it prove that the others can't?

Show answer 
sudo tcpdump -i eth0 port 443 -n

tcpdump shows the actual packets crossing an interface — it answers "is traffic arriving at all" at a level below what any application or socket-state tool can see. If nothing shows up here for a supposedly-open port, the packet isn't reaching this NIC — a firewall rule upstream, a security group, or the wrong interface is a much stronger suspect than the service itself.

Performance

"The server is slow" — slow how?

A vague ticket says a server is slow. You need to figure out in under a minute whether this is CPU-bound, memory-bound, or disk-bound before digging further.

Show answer 
top          # quick live overview, sorted by CPU
vmstat 2 5   # 5 samples, 2 seconds apart — CPU/memory/swap trend
free -h      # how much memory is actually free vs. cached
iostat -x 2  # per-device %util — is a disk saturated?

Run them in that order: top for a fast overall read (watch load average and which process dominates), vmstat's wa column for I/O wait (high wa with idle CPU points at disk, not CPU), free to rule out a memory/swap thrash, and iostat -x to confirm which device is actually saturated if disk looks like the culprit. Guessing which resource is the bottleneck without checking is how you "fix" the wrong thing.
