Overview

What Week 9 covers

You've already managed local users (Week 4, Module 3) and services (Week 5). Module 5 asks the security question behind both of them. When someone logs in, runs sudo, mounts a share or restarts a service, what decides whether that's allowed, and where does it get written down? On a real network the answer is rarely just /etc/passwd. Accounts usually live in a directory (LDAP or Active Directory), passwords get checked with Kerberos tickets, and a stack of PAM modules ties it all together on each box.

  • Define authentication, authorization and accounting, and name the Linux tool for each
  • Read a PAM stack in /etc/pam.d/: module types and control flags
  • Explain what polkit authorizes that sudo doesn't, and read a .rules file
  • Describe how SSSD, realm and Winbind join a Linux box to a directory
  • Read an LDAP distinguished name and run a basic ldapsearch
  • Walk through a Kerberos login: KDC, TGT, service ticket, kinit/klist
  • Share and connect to an SMB share with Samba (smb.conf, testparm, smbpasswd)
  • Find who logged in, and who failed to, with journalctl, last/lastb and auditd
Supplement, not a replacement: this page follows the Ascend 5.1 topic list (Polkit, PAM, SSSD/Winbind realm, LDAP, Kerberos, Samba, Logging) but is written independently. Use it to drill the vocabulary and the "which tool answers this?" reflex. Ascend has the full reading, and Lab 5.1 in ExtremeLabs is where you get the hands-on reps with a real directory. Don't experiment with PAM on the LFS host VM; one bad line can lock you out of the box you're building on.

Closer look

Reading a PAM stack

PAM is the piece most likely to show up as "read this config and say what happens." Each file in /etc/pam.d/ is named after the program that uses it, and each line has three parts: a type, a control flag and a module with its options. Lines of the same type run top to bottom.

# /etc/pam.d/example  (type   control     module         options)
auth       required    pam_faillock.so preauth deny=5 unlock_time=900
auth       sufficient  pam_sss.so
auth       required    pam_unix.so     try_first_pass
account    required    pam_unix.so
password   requisite   pam_pwquality.so retry=3 minlen=12
session    optional    pam_systemd.so
Four types = four separate stacks. A program calls PAM at different moments: auth lines run when you type your password, account lines run right after, session lines run as the login opens and closes, and password lines run only when you change a password. Control flags only act inside their own type. So a sufficient line under password can never let someone log in, and a requisite failure under account stops the account checks, not the auth ones. Read a PAM file one type at a time, not straight down the page.
The four module types
TypeQuestion it answersTypical modules
authIs this really you? (password, key, token)pam_unix, pam_sss, pam_faillock
accountEven if it's you, is the account allowed in right now? (expired, locked, wrong time or group)pam_unix, pam_access, pam_nologin
passwordRules for changing a passwordpam_pwquality, pam_unix
sessionSetup and teardown around the login (limits, home dir, logging)pam_limits, pam_mkhomedir, pam_systemd
Control flags: what happens on pass / fail
FlagIf it passesIf it fails
requiredKeep goingThe result will be fail, but the rest of the stack still runs (so an attacker can't tell which step failed)
requisiteKeep goingStop now and fail immediately
sufficientStop now and succeed, if nothing required above it already failedIgnored; keep going
optionalOnly matters if it's the only module of that typeOnly matters if it's the only module of that type
include / substackPull in another file's lines (e.g. Debian's @include common-auth, RHEL's system-auth)
Distro split: Debian/Ubuntu share common lines through /etc/pam.d/common-*, edited with pam-auth-update. RHEL/Fedora generate system-auth and password-auth with authselect, so hand edits there get overwritten. Either way, keep a root shell open in a second terminal while you change PAM, and test a fresh login before you close it.

Applied

Worked examples

Think it through before you expand the answer.

PAM

Lock an account after five bad passwords

Policy says an account locks for 15 minutes after five failed logins. A user named dana mistyped their password five times and is now locked out. Which PAM module enforces the policy, and how do you see and clear their failures?

Show answer 
# the policy, in /etc/security/faillock.conf
deny = 5
unlock_time = 900

sudo faillock --user dana     # list recorded failures
sudo faillock --user dana --reset

pam_faillock counts failures and refuses the auth step once the count hits deny. It replaced the older pam_tally2, which you'll still see in old guides. The settings can go on the PAM line or in faillock.conf; on RHEL you turn it on with authselect enable-feature with-faillock instead of editing the file by hand.

polkit

Let a group restart one service without sudo

The web team (group webops) needs to run systemctl restart nginx without a password. You don't want to hand them sudo at all. What do you write, and where?

Show answer 
// /etc/polkit-1/rules.d/50-webops-nginx.rules
polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.systemd1.manage-units" &&
        action.lookup("unit") == "nginx.service" &&
        subject.isInGroup("webops")) {
        return polkit.Result.YES;
    }
});

When a regular user runs systemctl restart, systemctl doesn't become root. It asks systemd over D-Bus, and systemd asks polkit whether to allow it. Rules are JavaScript files read in filename order. Return YES, NO or AUTH_ADMIN (ask for an admin password); return nothing to let the next rule decide. pkaction lists the action IDs you can match on. Each ID is defined, with its default answer, in an XML .policy file under /usr/share/polkit-1/actions/ that the package installs. Your .rules file overrides that default; don't edit the .policy file, because an update will replace it.

SSSD

SSSD won't start after you edited its config

You copied a working sssd.conf from a teammate's laptop. Now systemctl status sssd shows failed, and the journal complains about the config file. The contents are identical. What's different?

Show answer 
ls -l /etc/sssd/sssd.conf
sudo chown root:root /etc/sssd/sssd.conf
sudo chmod 600 /etc/sssd/sssd.conf
sudo systemctl restart sssd
getent passwd jsmith@corp.example.com    # does the lookup work now?

The config can hold a bind password, so SSSD refuses to read it unless it's owned by root and readable only by root. Copying usually leaves it at 0644. Once it starts, getent proves NSS can resolve directory users. If an old answer is cached, sss_cache -E clears it.

realm

Join a Linux server to Active Directory

A new Ubuntu server needs to accept logins from the CORP.EXAMPLE.COM AD domain, and only the linux-admins group may log in. What's the shortest path?

Show answer 
realm discover corp.example.com           # what is it, what packages are needed?
sudo realm join -U Administrator corp.example.com
realm list                                # confirm: configured, client-software: sssd
sudo realm permit -g linux-admins@corp.example.com

realm (realmd) does the work you'd otherwise do by hand. It finds the domain through DNS, creates the computer account, writes sssd.conf and krb5.conf, and fetches a keytab. realm permit is authorization: everyone can still authenticate, but only that group is allowed in. DNS has to point at the domain controllers, or discovery fails before anything else happens.

Kerberos

"Clock skew too great"

Logins with a domain account worked yesterday. Today kinit jsmith fails with a clock-skew error, and the password is definitely right. What's wrong, and what tools confirm it?

Show answer 
timedatectl                  # "System clock synchronized: no"?
chronyc tracking             # how far off, and from which source
sudo systemctl restart chronyd     # "chrony" on Debian/Ubuntu
kinit jsmith && klist         # should now show krbtgt/CORP.EXAMPLE.COM@...

Kerberos tickets carry timestamps to stop replay attacks. By default, if the client and KDC clocks are more than 5 minutes apart, the KDC rejects the request. Time sync isn't optional on a Kerberos network, which is where Module 4's chrony comes back. klist shows your tickets and their expiry; kdestroy throws them away.

LDAP

Find one user in the directory

You need to confirm the directory server has an entry for jsmith and see which groups they're in. The base of the tree is dc=corp,dc=example,dc=com.

Show answer 
ldapsearch -x -H ldaps://ldap.corp.example.com \
  -D "cn=reader,dc=corp,dc=example,dc=com" -W \
  -b "dc=corp,dc=example,dc=com" "(uid=jsmith)" cn memberOf

Read it piece by piece. -x means simple bind (username and password). -H is the server, here LDAPS on 636 so the password is encrypted. -D/-W bind as a reader account and prompt for its password. -b is where to start searching, then the filter, then the attributes to return. The full name of that entry is a DN like uid=jsmith,ou=People,dc=corp,dc=example,dc=com, read from the most specific part on the left to the root on the right.

Samba

Share a folder with Windows users

Accounting wants a share called reports pointing at /srv/reports, writable only by the acct group. You've added the section to smb.conf, but user lee gets "access denied" even though lee is a Linux user in that group.

Show answer 
[reports]
   path = /srv/reports
   valid users = @acct
   writable = yes

testparm                            # check the file's syntax
sudo smbpasswd -a lee               # give lee a Samba password
sudo systemctl restart smbd         # smb on RHEL/Fedora
smbclient //localhost/reports -U lee

In a standalone setup, Samba keeps its own password database, separate from /etc/shadow, so a Linux account isn't enough. smbpasswd -a adds lee. Run testparm after every edit to catch typos. Linux permissions on /srv/reports still apply underneath, and on RHEL/Fedora SELinux has to allow the share too (Week 10).

Accounting

Who tried to get in last night?

A manager asks whether anyone tried to SSH into a server overnight, and whether anyone actually succeeded. Where do you look?

Show answer 
journalctl -u ssh --since yesterday | grep -E "Failed|Accepted"   # sshd on RHEL/Fedora
sudo lastb | head          # failed logins (btmp); not on Debian 13+
last | head                # successful logins and reboots (wtmp)
sudo grep sshd /var/log/auth.log    # Debian/Ubuntu text log, if rsyslog is installed
sudo grep sshd /var/log/secure      # RHEL/Fedora text log

The journal is the one source every systemd distro has. The text files depend on rsyslog: a fresh Debian 12+ install doesn't include it, so /var/log/auth.log may not exist at all. Debian 13 also moved last into the wtmpdb package and dropped lastb; there, failed logins come from the journal. Learn both tools anyway, because the exam still asks about them. For "who opened this file?" questions that logins can't answer, auditd records events you choose with auditctl -w /etc/shadow -p wa, and you search them with ausearch and summarize with aureport.

Lab connection

Where this shows up in your LFS build

Your 9.2–15.2 lab is building Linux from source. That puts you on the other side of every tool on this page: instead of configuring them, you get to see where they come from, and which ones a minimal system doesn't have at all.

  • The lfs user (Ch. 4). You build as an unprivileged user with a stripped, clean environment (env -i in .bash_profile), not as root. That's least privilege: a mistake can't wreck the host.
  • Shadow (Ch. 8). This package gives you passwd, useradd, login and the /etc/shadow file itself. The book has you pick the hash method in /etc/login.defs.
  • Libxcrypt (Ch. 8). This library provides crypt(), which turns a password into the hash in /etc/shadow. The prefix tells you the algorithm: $y$ is yescrypt, $6$ is SHA-512.
  • What's missing. LFS installs no Linux-PAM, polkit, SSSD, Kerberos or Samba. Linux-PAM, polkit, MIT Kerberos and Samba are in the follow-on book (BLFS). A system that works with none of them is a good way to see that they're layers added on top, not part of the core.
