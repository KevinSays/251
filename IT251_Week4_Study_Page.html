Concepts

Two ways to see it

The account lifecycle shows what stage a user is in. Process states show what a running process is doing right now. Inodes and links show why a filename isn't the same thing as the file.

Applied

Worked examples

Think it through before you expand the answer.

Links

Which link survives?

You create a hard link and a symbolic link to the same file, then delete the original file. What happens to each link?

Show answer

Hard link: still works — it shares the same inode as the original, so the data is still there under the link's name.

Symbolic link: broken — it only stored a path to the original filename, which no longer exists.

Accounts

Temporarily disable, don't delete

A user is going on leave for a month. You need to prevent login without losing their account, files, or group memberships.

Show answer 
sudo passwd -l theirusername
# or: sudo usermod -L theirusername

This locks the password (prefixes the hash) instead of deleting the account — userdel would be permanent and wrong here.

Process management

Kill it, but nicely first

A process is hung and needs to stop. What's the right order of signals to try?

Show answer 
kill -SIGTERM <pid>   # ask nicely — lets it clean up
# still stuck?
kill -SIGKILL <pid>   # force — no cleanup, last resort

SIGTERM (15) gives the process a chance to close files/save state; SIGKILL (9) can't be caught or ignored, but skips any cleanup — reach for it only after SIGTERM fails.

/etc/passwd

Read the fields

A line in /etc/passwd reads: svc_backup:x:998:998:Backup Service:/var/lib/backup:/usr/sbin/nologin. Is this a regular user, and could someone SSH in as this account?

Show answer

Not a regular user. UID/GID 998 falls in the system-account range on most distros (well below the 1000+ regular-user range), and the shell field is /usr/sbin/nologin — this account exists to run a service, not for a person to log into. Nobody can get an interactive shell as svc_backup even with the right password, because nologin immediately rejects the login attempt.

Device types

Block or character?

ls -l /dev shows two entries: brw-rw---- ... sda and crw-rw-rw- ... null. What does the leading b vs. c actually tell you?

Show answer

b = block device (/dev/sda) — addressable in fixed-size chunks, the category disks fall into. c = character device (/dev/null) — a continuous stream, read/written one byte at a time, the category serial ports, terminals, and pseudo-devices like /dev/null//dev/random fall into. It's the same first-column position where a regular file shows - and a directory shows d.

Process states

Is this a problem?

ps aux shows a process with STAT = Z that's been sitting there for an hour. Should you kill -9 it?

Show answer

You can't kill a zombie — it's already dead; kill has nothing left to signal. A zombie lingers because its parent hasn't called wait() to collect its exit status yet. The real fix targets the parent: if it's still running, it has a bug (not reaping children); if the parent itself is gone, the zombie gets reparented to init/systemd, which reaps it automatically. Either way, a lingering zombie isn't consuming real CPU/memory — it's mostly a diagnostic signal, not an emergency.
