Overview

What Week 10 covers

Week 9 asked who you are and what you're allowed to do. This week builds the walls around that. A firewall decides which packets get to the system at all. Hardening assumes something will get through anyway, and makes sure it finds as little as possible: no extra services, no stray SUID programs, no root SSH logins, and a mandatory access control layer that says "no" even to root-owned processes that go off-script.

  • Explain how netfilter hooks, tables and chains process a packet
  • Read and write a basic nftables ruleset, and know where iptables and ipset fit today
  • Use firewalld zones and services, and the runtime vs. permanent split
  • Use ufw on Ubuntu-family systems
  • Explain stateful vs. stateless filtering, NAT (SNAT, masquerade, DNAT) and IP forwarding
  • Control privilege with sudo; protect files with chattr, special bits and ACLs
  • Tell SELinux from AppArmor, and fix the most common SELinux denial
  • Harden SSH, remove insecure services and unneeded SUID bits, and explain Secure Boot
Supplement, not a replacement: this page follows the Ascend 5.2 and 5.3 topic lists and is written independently. Ascend has the full reading, and Labs 5.2 and 5.3 in ExtremeLabs are where you practice on real rulesets. If you try firewall rules on your own VM, do it from the VirtualBox console, not over SSH: a wrong policy drop cuts off the connection you're typing into.

Closer look

Reading an nftables ruleset

nftables is the current packet filter on Debian, Ubuntu, RHEL and Fedora, so learn its shape first. A table is a container tied to an address family (inet covers IPv4 and IPv6 together). A base chain attaches to a netfilter hook and has a default policy. Rules are checked top to bottom, and the first one that gives a verdict (accept, drop, reject) wins.

#!/usr/sbin/nft -f
# /etc/nftables.conf (Debian/Ubuntu)   /etc/sysconfig/nftables.conf (RHEL/Fedora)
flush ruleset

table inet filter {
    set ssh_admins {                       # a built-in set: no ipset needed
        type ipv4_addr
        flags interval
        elements = { 192.168.56.0/24 }
    }

    chain input {
        type filter hook input priority filter; policy drop;

        ct state established,related accept   # stateful: replies to our own traffic
        ct state invalid drop
        iif "lo" accept                       # loopback
        ip protocol icmp accept               # let ping work
        ip saddr @ssh_admins tcp dport 22 accept
        tcp dport { 80, 443 } accept
    }

    chain forward {
        type filter hook forward priority filter; policy drop;
    }
}

Stateful vs. stateless: the ct state established,related accept line is what makes this firewall stateful. Connection tracking remembers that you opened a connection out, so the replies get in without a rule for every port. A stateless filter judges each packet alone. It's simpler and a little faster, but you'd have to allow return traffic by hand, which in practice means opening far more than you meant to.

Closer look

Hardening: the layers

A file access has to pass every layer below. Standard permissions and ACLs are the discretionary layer: the owner decides. SELinux or AppArmor is the mandatory layer: policy decides, and the owner, even root, can't override it from inside the policy. If any layer says no, the answer is "Permission denied."

Access control layers
LayerDecides byTools
Permissions (DAC)Owner / group / other, rwx, plus SUID, SGID, stickychmod, chown, umask
ACLs (DAC)Extra named users or groups on one file. Part of the same permission check; ls -l shows a +getfacl, setfacl -m u:lee:rw file
AttributesFilesystem flags that block changes, even by root: i immutable, a append-onlychattr +i, lsattr
SELinux (MAC)Labels (contexts) on every process and file; policy says which process types may touch which file typesgetenforce, ls -Z, restorecon, semanage, setsebool
AppArmor (MAC)Per-program profiles listing which paths it may useaa-status, aa-complain, aa-enforce

Applied

Worked examples

Think it through before you expand the answer. Three of these start from something already broken, because that's how the exam asks.

firewalld

The web port worked until the reboot

On a Fedora web server you ran sudo firewall-cmd --add-service=http. The site loaded. After a reboot it's unreachable again. What happened, and what's the right sequence?

Show answer 
sudo firewall-cmd --get-active-zones            # which zone is the NIC in?
sudo firewall-cmd --zone=public --add-service=http --permanent
sudo firewall-cmd --reload
sudo firewall-cmd --zone=public --list-services  # http should be listed

firewalld keeps two configs. Runtime is what's loaded now; permanent is what's on disk for the next start. A command without --permanent only changes runtime, so it vanished on reboot. Either add with --permanent and --reload, or test in runtime first and then save it with firewall-cmd --runtime-to-permanent. Rules belong to a zone, and an interface belongs to one zone, so check the zone first.

ufw

SSH from the admin network only

An Ubuntu server should accept SSH only from 192.168.56.0/24, accept HTTPS from anywhere, and refuse everything else inbound. You're on the console, and ufw is installed but inactive.

Show answer 
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.56.0/24 to any port 22 proto tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status numbered        # delete a rule with: sudo ufw delete 3

Set the defaults and the SSH rule before ufw enable. Enabling a default-deny firewall over SSH without the allow rule locks you out. ufw saves its rules on its own, and they survive reboots once enabled.

Troubleshoot

The rule is there, but it doesn't work

A teammate needed port 8080 open. They ran sudo nft add rule inet filter input tcp dport 8080 accept, and nft list ruleset shows the rule. Clients still time out. ss -tlnp shows the app listening on 0.0.0.0:8080. Here's the chain:

chain input {
    type filter hook input priority filter; policy accept;
    ct state established,related accept
    tcp dport 22 accept
    drop
    tcp dport 8080 accept
}
Show answer

Rules run top to bottom, and the bare drop catches everything before the new rule. nft add appends to the end of the chain. Delete the misplaced rule and insert it above the drop instead:

sudo nft -a list chain inet filter input        # -a shows each rule's handle
#   drop # handle 4
#   tcp dport 8080 accept # handle 5
sudo nft delete rule inet filter input handle 5
sudo nft insert rule inet filter input position 4 tcp dport 8080 accept   # goes in before handle 4

To prove it from the Week 7 toolkit: sudo tcpdump -ni any port 8080 shows the SYNs arriving with no reply, and ss shows no new connections. That points at a filter on this box, not the network or the app. A cleaner design is policy drop on the chain instead of a hand-written drop line, so new rules added at the end still work.

NAT

Turn a Linux box into a NAT gateway

A VM has eth0 on the internet side and eth1 on an internal 10.10.0.0/24 network. Internal hosts use it as their gateway but can't reach anything. What two things does the kernel need?

Show answer 
sysctl net.ipv4.ip_forward                       # 0 = not routing
echo 'net.ipv4.ip_forward = 1' | sudo tee /etc/sysctl.d/90-forward.conf
sudo sysctl --system

# then masquerade traffic leaving eth0 (nftables)
table ip nat {
    chain postrouting {
        type nat hook postrouting priority srcnat;
        oifname "eth0" masquerade
    }
}

First, forwarding: by default Linux drops packets that aren't addressed to it. Only turn this on for boxes that are meant to route. Second, source NAT: internal addresses are private, so replies from the internet can't find them. masquerade rewrites the source to eth0's address on the way out, and conntrack reverses it for replies. Use masquerade when that address comes from DHCP, and snat to 203.0.113.10 when it's fixed. The opposite direction, sending inbound port 80 to an internal server, is DNAT in prerouting. Also check that the forward chain allows the traffic.

SUID

Audit the SUID programs

A hardening checklist says "remove unnecessary SUID bits." How do you find them, and how do you decide which ones to remove?

Show answer 
sudo find / -xdev -type f -perm -4000 -ls 2>/dev/null   # SUID
sudo find / -xdev -type f -perm -2000 -ls 2>/dev/null   # SGID
sudo chmod u-s /usr/bin/some-unneeded-tool

A short list is normal: passwd, su, sudo, mount, and a few more. Every SUID-root program is a way to run code as root if it has a bug, which is why attackers run this same find right after they get in. Look up anything unfamiliar, and remove the bit, or the whole package, if nothing needs it. Watch for SUID files in home directories or /tmp; those are a red flag.

Attributes

Even root can't edit this file

You're root, but echo nameserver 1.1.1.1 > /etc/resolv.conf says "Operation not permitted". Permissions are -rw-r--r-- root root. What's stopping root?

Show answer 
lsattr /etc/resolv.conf          # ----i---------e------- = immutable
sudo chattr -i /etc/resolv.conf  # remove it, make the change, then:
sudo chattr +i /etc/resolv.conf

The i (immutable) attribute blocks writing, deleting, renaming and linking, for everyone including root, until someone removes it with chattr -i. Admins use it to protect files that shouldn't change; attackers use it to make their backdoors hard to delete. The a (append-only) attribute is the log-file version: you can add lines, but you can't change or remove old ones. "Operation not permitted" for root is the clue; ordinary permission problems say "Permission denied."

SELinux

Apache returns 403 for files you just moved in

On Rocky Linux you built a site in your home directory, then ran sudo mv ~/site/* /var/www/html/. The permissions are fine (644, readable by everyone), but Apache returns 403 Forbidden. Setting setenforce 0 makes it work.

Show answer 
ls -Z /var/www/html/                      # user_home_t: wrong type
sudo ausearch -m avc -ts recent           # the denial, from the audit log
sudo restorecon -Rv /var/www/html/        # relabel to httpd_sys_content_t
sudo setenforce 1                         # and turn enforcement back on

mv keeps a file's SELinux label, so the files still say user_home_t, and the policy won't let the web server (httpd_t) read home-directory files. cp would have given them the destination's label. restorecon resets labels to what the policy expects for that path. For a custom web root, first tell the policy about it with semanage fcontext -a -t httpd_sys_content_t "/srv/web(/.*)?", then run restorecon. Leaving SELinux in permissive mode "because it fixed it" is the wrong answer on the exam and on the job. The Ubuntu version of this problem is an AppArmor profile: check aa-status and the journal for apparmor="DENIED".

SSH

Harden sshd without locking yourself out

Policy: no root login, keys only, and only the admins group may log in. How do you apply it safely?

Show answer 
ssh-keygen -t ed25519            # on your workstation
ssh-copy-id you@server           # install the public key, then test a key login

# /etc/ssh/sshd_config.d/10-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
AllowGroups admins

sudo sshd -t                      # syntax check: silence means OK
sudo systemctl reload ssh         # sshd on RHEL/Fedora
# keep this session open; test a NEW login in a second terminal

Get a working key login before turning passwords off. sshd -t catches typos that would stop the daemon from starting. Watch out: in sshd_config, the first value read for a setting wins. Drop-in files are included at the top of the main file, which is why they override it. Add fail2ban to block repeated failures, and use a jump host (ssh -J bastion target) so internal servers don't face the internet. On those servers, allow SSH only from the bastion with a firewall source rule (like the ssh_admins set above) or AllowUsers you@10.0.0.5. Older guides use /etc/hosts.allow for this, but current OpenSSH no longer reads it. Telnet, FTP and rsh send passwords in cleartext; replace them with SSH and SFTP and remove the packages.

Secure Boot

The new driver won't load

After installing a third-party driver from source (DKMS) on a UEFI laptop, modprobe fails with "Key was rejected by service." What's going on?

Show answer 
mokutil --sb-state                 # SecureBoot enabled
dmesg | grep -i -E "secure|lockdown"
sudo mokutil --import MOK.der      # your signing key's public half; confirm at next boot

With Secure Boot on, UEFI firmware runs only a signed boot loader (the signed shim, then GRUB). That chain checks the kernel's signature, and on most distros the kernel then refuses unsigned modules. DKMS can create a key and sign its modules for you; where it keeps that key varies by distro. The fix is to sign the module and enroll the key as a Machine Owner Key (MOK), not to turn Secure Boot off. This is what stops a rootkit from slipping in a modified boot loader or kernel module.

Lab connection

Where this shows up in your LFS build

This week's lab builds your cross-toolchain. A finished LFS system is a good hardening case study: it starts small, and everything that's there, you put there.

  • No firewall at all. LFS installs neither nft nor iptables; both are in BLFS. Netfilter itself is kernel code, so in 13.2 the kernel config decides whether your system could filter packets (Networking support → Networking options → Network packet filtering framework).
  • Small attack surface by default. No SSH server, no web server, no extra daemons. That's the "avoid, disable and remove" goal, reached by never installing them.
  • SUID audit. After Ch. 8, run the SUID find from the examples inside your chroot, with / as the start. Compare its short list with your Debian host's.
  • chattr and lsattr come from E2fsprogs, which you build in Ch. 8.
  • No Secure Boot. The class VM boots with BIOS and MBR, and the kernel you compile isn't signed. On a Secure Boot machine, firmware would refuse to load it unless you signed it and enrolled your own key, which is exactly the protection that example describes.
