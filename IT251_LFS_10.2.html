Every session · keep long builds alive

Work inside tmux

A build runs inside your SSH window. If that window closes, your Wi-Fi drops, or you close your laptop's terminal, the build is killed halfway. tmux fixes this: it keeps your session running inside the VM, and you can reconnect to it later. Start it first every time you sit down to build, as student, before sudo -i:

tmux new -s lfs          # first time: start a session named "lfs"
tmux attach -d -t lfs    # every time after: reconnect to it (also after an SSH drop)
  • To leave a build running and close the window, press Ctrl+b, let go, then press d ("detach"). The build keeps going.
  • A green bar at the bottom of the window means you're inside tmux.
  • If tmux attach says no sessions, the VM was rebooted (that ends tmux too). Start a new one, run your resume card, and redo the package you were on.
  • Why the -d? It kicks off any old connection that's still hanging on to your session. That happens most after you save the VM's state in VirtualBox ("Save the machine state" when you close it) in the middle of a build. Saving the state is safe: the build is frozen and picks up right where it stopped when you start the VM again. But your old SSH window died while the VM was frozen, and tmux may still think it's there. If you reconnect with a plain tmux attach, part of your screen fills with rows of dots (·····), because tmux is sizing everything to the old, dead window. Nothing is broken. Press Ctrl+b, let go, press d, then run tmux attach -d -t lfs.
  • tmux can't help if your laptop goes to sleep, because the whole VM pauses. See Keep your laptop awake.

The habit that saves you: one package, start to finish

Chapters 5–8 are about 100 packages, and every one follows the same routine from the book's General Compilation Instructions. Learn it once on a small package and the rest is repetition.

  1. Run your resume card (Card 2 for Chapters 5–6), inside tmux.
  2. Go to the sources and find the exact file name. Don't guess version numbers; let the shell show you: 
    cd $LFS/sources
ls | grep -i m4          # shows: m4-1.4.21.tar.xz
  3. Extract it and go into the new folder. The folder has the same name without .tar.xz. Press Tab to complete long names instead of typing them. 
    tar -xf m4-1.4.21.tar.xz
cd m4-1.4.21
  4. Open the package's page in the book and run its commands one grey box at a time, top to bottom. Copy the whole box (some boxes are several lines joined by \; they're one command), paste it, press Enter, wait for the prompt to come back, and check it worked before the next box.
  5. Leave and delete the folder, even if everything worked. The tarball stays; only the extracted copy goes: 
    cd $LFS/sources
rm -rf m4-1.4.21
  6. Tick it off in your journal (book section + "done"), then go to the next package.
Worked example · §6.2 M4

The first package of Chapter 6, all the way through

This is exactly what one package looks like, using the commands from §6.2 as they appear in the 13.1-systemd book. For every other package, take the commands from the book itself, not from here.

# Start: go to the sources, extract, enter the folder
cd $LFS/sources
tar -xf m4-1.4.21.tar.xz
cd m4-1.4.21

# Box 1: a settings file the book asks for here (paste all 4 lines together)
cat > $LFS/usr/share/config.site << EOF
ac_cv_func_posix_spawn_file_actions_addchdir=yes
ac_cv_func_posix_spawn_file_actions_addfchdir=yes
EOF

# Box 2: "Prepare M4 for compilation" (3 lines, one command)
./configure --prefix=/usr   \
            --host=$LFS_TGT \
            --build=$(build-aux/config.guess)
echo $?                  # 0 = it worked. Anything else: stop.

# Box 3: "Compile the package"
make
echo $?                  # 0

# Box 4: "Install the package"
make DESTDIR=$LFS install
echo $?                  # 0

# Finish: leave the folder and delete it
cd $LFS/sources
rm -rf m4-1.4.21

The echo $? lines are ours, not the book's. They're an easy way to check each step (see below). Lines starting with # are comments, so you don't need to type them.

Did it work? Thousands of lines scrolling past is normal. Only the end of the output matters.
  • Run echo $? right after a command. It prints that command's exit status: 0 means success, and any other number means it failed. (It only reports the most recent command, so run it right away.)
  • Failure looks like make: *** [...] Error 1 (or Error 2), or configure: error: …, in the last few lines. Stop there. Don't run the next box.
  • Lines with warning: are fine. Compilers print lots of them, and the book expects that.
  • A failed test in the Chapter 8 test suites is not a failed build. See Test suites.
If a package fails: don't try to fix it in place. Copy the last ~30 lines into your journal, then cd $LFS/sources, rm -rf the folder, extract again, and redo the whole package, comparing each command with the book character by character. Still failing? See Common snags.

What's actually happening

Concept

Why build the compiler twice?

Your Debian GCC makes programs that link against Debian's C library. Chapter 5 builds a cross-compiler with a different name (x86_64-lfs-linux-gnu-gcc, from $LFS_TGT) that only looks inside $LFS. Because its name is different, nothing can accidentally use the host's tools or libraries. Chapter 6 uses it to build temporary tools that are already inside your new system. The Toolchain Technical Notes explain this in depth. Read them; they're the heart of LFS.

Checkpoint

The Chapter 5 sanity check (§5.5)

After Glibc, the book has you compile an empty C program with the new toolchain and inspect it with readelf. The output must name the new dynamic linker, [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]. If it doesn't, stop: everything after this depends on it. Screenshot it for M2.
